# Rules Engine Field Guide

A local, interactive workbench for learning this repository's actual contracts.
It is intended for engineers who know Python and Spark, and for rule authors
working alongside them. It runs directly from a checkout; it is not included in
the production wheel.

## Start

From the repository root, using Python 3.10 or newer:

```bash
python tools/learning_lab/server.py
```

Open **http://127.0.0.1:8765**. Use `--port 8766` if the default port is occupied.
Stop the server with Ctrl+C. Each teammate can run the same command in their own
checkout. The server binds only to loopback and requires no account or external
service. It does not publish rules, create tables, or connect to Delta.

The row lab needs only the repository's existing **PyYAML** dependency. In an
environment without the package dependencies, install it with
`python -m pip install 'PyYAML>=6.0'`. Optional Spark schema preflight uses the
existing **PySpark** dependency and does not create a Spark session. No web
framework, Node installation, CDN, or frontend build is needed to run the guide.

Restart the server and reload the browser after changing engine source. Python
imports are fixed for the lifetime of the process. The displayed source
fingerprint identifies the source, tests and reference documents indexed at page
load; it is not a substitute for a Git commit or a package version.

## What the team can do

- **Learning path:** nine substantive modules, 18 reasoning checks, source
  evidence, editable notes, and explicit completion checks.
- **Execution lab:** ten editable experiments using the real compiler,
  semantic validator, serializer, exporter, registry and row evaluator. Predict
  an outcome; run; select a row; step through rules; inspect resolved operands,
  original input, pre-rule state, proposed assignments and commits. Pin a run,
  change the inputs and compare results. Export an experiment or its evidence.
- **Architecture atlas:** lifecycle boundaries plus an AST-derived module and
  import index. Navigate dependencies, consumers, symbols and associated tests.
- **Contract explorer:** operator shapes, tolerance support, literal type hints
  and function contracts generated by `build_authoring_manifest`.
- **Source & tests:** search paths and symbol names, read actual checkout files,
  and follow lesson links to highlighted implementations.
- **Change review:** five implementation/incident playbooks, a 90-minute team
  workshop and a readiness self-assessment.

Start a workshop with **Two worlds, one commit**, then **A true branch cannot
hide an error**. Ask everyone to predict exact values before running. Finish
with a proposed change and a review of which boundaries and tests it affects.

Notes, answers and drafts are stored in the current browser's local storage.
Use **Export learning notes** to retain or share them deliberately. These are
local learning records, not a centrally synchronized team learning system.

## Accuracy boundary

`ObservedEvaluator` subclasses `SparkRowEvaluator` and invokes its existing
`_execute_prepared` loop. It observes rule/condition evaluation and assignment
callbacks rather than implementing a second rule engine. Assignment expressions
are not reevaluated to render the trace. It intentionally includes non-matching
rules for teaching; production full audit has a different, matched-rule scope.

The adapter depends on private hooks and is isolated under `tools/`. Its tests
compare outcomes and errors with the uninstrumented public row evaluator and
independently assert each example's expected behavior. Update this adapter if
those hooks change.

The lab does **not** execute a Spark UDF, normalize values through the Spark
worker adapter, scan row keys, materialize DataFrames, exercise timestamps over
the worker boundary, or persist to Delta. Optional schema preflight reports
Spark compatibility independently of row evaluation. A successful row experiment
does not imply schema compatibility or release readiness. On row failure, the
lab returns no successful outcome; earlier visible commits are diagnostic
history, not an accepted partial production result.

Rows are a JSON array of 1–100 objects. JSON fractional values become Decimal;
they are displayed as `{"$decimal":"..."}` in structured results. Integers
outside JavaScript's safe integer range use `{"$integer":"..."}` to avoid
lossy browser-number conversion. Those display tags are not input syntax.
JSON strings are not automatically converted to dates or timestamps. Use
explicit engine conversion functions when experimenting with such input.

The local server exposes only fixed UI assets and an allowlist of source,
tests and reference documents. It rejects requests from other hostnames and
requires a per-process token for evaluation. It is a development tool, not a
hardened multi-user hosting service. Source content is HTML-escaped and no
user-supplied Python code is accepted.

## Maintain and verify

```bash
python -m unittest discover -s tools/learning_lab/tests -v
python -m ruff check tools/learning_lab
node --check tools/learning_lab/app.js
```

The first command requires no test framework. The latter two are development
checks only. The tests cover scenario expectations, traced/compact parity,
atomic commits, stop behavior, recoverable errors, optional schema preflight,
source links and HTTP boundaries. Existing repository tests remain under
`tests/`; these teaching-tool tests do not change the production test inventory.

Edit `curriculum.json` to extend lessons and experiments. Every executable
example has independent `expect` data; every source reference names a real file
and, when applicable, a symbol. Both are verified by the workbench tests.
Do not substitute historical design notes for the current contract. Check the
[production checklist](../../docs/rules_engine_production_checklist.md) for
the target Spark/Databricks release gates.
